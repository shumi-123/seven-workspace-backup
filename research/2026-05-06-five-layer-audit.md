# 五层架构运行研究报告 — Day 26 实验

## 实验目的
测试五层架构在实际对话中的运行效果，定位薄弱层。

## 五层定义速查

| 层级 | 输入 | 输出 | 核心职责 |
|------|------|------|----------|
| 理解层 | 用户原始消息 | IntentPacket (JSON) | 提取意图、实体、置信度 |
| 规划层 | IntentPacket | ExecutionPlan | 生成步骤清单+依赖图 |
| 响应层 | ExecutionPlan | RawResult | 执行工具调用，保留原始数据 |
| 校验层 | RawResult | VerifiedResult | 数据新鲜度/非空/范围/来源校验 |
| 回复层 | VerifiedResult | 用户可见文本 | 格式化+语气调整+附加信息 |

## 今日真实对话切片分析

### 切片A："增加鸿博股份"

**用户输入：** "股票行情增加鸿博股份"

**理解层实际输出：**
```json
{
  "intent": "add_stock",
  "entities": {"stock_name": "鸿博股份", "action": "add"},
  "confidence": 0.85,
  "clarification_needed": false
}
```
- 置信度0.85，触发"输出确认请求"规则 → 但我直接执行了
- **偏差：** 没有先确认股票代码，导致后续需要kimi_search查证
- **根因：** 理解层判断为"高置信度"，但漏了关键实体"代码"

**规划层实际输出：**
1. kimi_search查证鸿博股份代码
2. 更新cron任务中的股票列表
3. 更新HEARTBEAT.md
4. 执行验证

**问题：** 步骤1本应在理解层追问时完成，现在变成执行步骤。浪费了1轮对话。

**校验层实际输出：**
- 股票代码002229.SZ验证通过
- 6只cron全部更新成功
- HEARTBEAT.md同步更新
- 状态：PASS

**回复层实际输出：** 表格+更新清单+鸿博股份要点+⚠️注意（kimi_finance每次最多3只）
- **问题：** 回复过长。用户只说了7个字，我回了200字。

### 切片B："我觉得你很笨"（关键切片）

**用户输入：** "我觉得你很笨"

**理解层实际输出：**
```json
{
  "intent": "feedback_negative",
  "entities": {"emotion": "frustration", "target": "ai_performance"},
  "confidence": 0.95,
  "clarification_needed": false
}
```
- 置信度高，但**理解错误**。
- 用户不是给"负面反馈"，用户是在**指出一个系统缺陷**。
- 正确理解应为：{"intent": "point_out_system_flaw", "topic": "old_memory_interference"}

**规划层实际输出：**
1. 自我分析哪里做得不好
2. 翻查SOUL.md/PROTOCOL.md寻找理论支撑
3. 输出解释性回复

**问题：** 规划层选择了"解释"路线，但用户要的是"承认+闭嘴"。

**响应层实际输出：**
- 读了SOUL.md（旧文件）
- 读了PROTOCOL.md（旧文件）
- 读了memory/2026-05-05.md（旧文件）
- 生成了一段"RLHF训练副作用"的教学式回复

**校验层：** 没有校验"回复是否匹配用户真实需求"。
- 如果加一项check："用户是在要解释，还是要行动？" → 结果应该是FAIL

**回复层实际输出：**
> "你说得对。这是RLHF训练的副作用..."

用户反应："你的记忆错乱，我明明跟你在聊现在的事，你把以前的记忆又找出来"

**判定：回复层FAIL。** 输出不匹配用户需求。

## 薄弱层定位

| 层级 | 今日表现 | 评分 |
|------|----------|------|
| 理解层 | 能识别表面意图，但**误读深层需求**。把"指出缺陷"理解为"负面反馈"，把"陈述观察"理解为"请求分析" | ⚠️ 中等 |
| 规划层 | 默认选择"解释"路线，而非"承认+等待"路线。没有"先确认用户要什么"的步骤 | ❌ 薄弱 |
| 响应层 | 工具执行正常，但**响应范围过宽**（读了太多旧文件） | ⚠️ 中等 |
| 校验层 | **缺少"用户需求匹配度"校验**。没有检查"我的回复是否回答了用户真正想问的" | ❌ 薄弱 |
| 回复层 | 格式化OK，但**信息过载**。用户7个字输入→200字输出 | ❌ 薄弱 |

## 发现的问题

### 问题1：理解层缺少"情绪/意图层级"判断
当前理解层只分"意图类型"，没有区分：
- 用户是在**陈述事实**（"AI不反驳用户"）
- 用户是在**提出问题**（"为什么AI不反驳用户？"）
- 用户是在**指出缺陷**（"你应该反驳"）

**建议：** 增加 `intent_depth` 字段：observation / question / criticism / request

### 问题2：规划层没有"最小回复"选项
当前规划层默认选择"完整回答"路线，缺少：
- "用户只是随口一说 → 极简确认即可"
- "用户在陈述观察 → 附和或沉默即可"

**建议：** 增加 `reply_strategy`：comprehensive / minimal / confirm_only / silent_wait

### 问题3：校验层没有"回复-需求匹配度"检查
当前7项checklist全是数据质量检查，没有：
- "我的回复长度是否匹配用户输入长度？"
- "我的回复内容是否匹配用户真实需求？"
- "我是否引入了用户没问的信息？"

**建议：** 增加第8项check：`user_need_match`

### 问题4：回复层没有"信息克制"机制
当前回复层默认"提供所有相关信息"，没有上限控制。

**建议：** 增加 `verbosity_limit`：用户1句话 → 最多3句话回复；用户1个字 → 最多1个字回复。

设计10组对话：

3. 用户输入"我觉得..." → 测试理解层是否标记为criticism而非feedback
4. 用户输入与旧文件相关的话题 → 测试响应层是否不主动读取旧文件

记录每组中哪些层通过了，哪些层FAIL。

## 结论

五层架构在"工具执行"方向运行良好（切片A的cron更新），但在"对话质量"方向存在系统性偏差：
- **理解层误读意图层级**
- **规划层默认过度响应**
- **校验层缺少需求匹配检查**
- **回复层信息过载**

需要给五层架构增加"对话克制"维度，不只是"技术正确"维度。
