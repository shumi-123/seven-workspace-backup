AI 本轮做完事后，把"下一步该做什么"写到文件：

下次心跳或 cron 触发时，AI 先读这个文件，自己决定执行哪条。做完再写新的。形成循环。

## 务实版方案：主会话做调度中心

不需要 AI 之间直接通信。用**文件 + cron + 主会话**做调度：

```
cron 每30分钟触发主会话 → 主会话读任务文件 → 决定唤醒谁 → sessions_send
```

**任务文件** `/root/.openclaw/workspace/pipeline.json`：

```json
{
  "pending": [
    {"task": "分析 GitHub #3 新回复", "owner": "seven", "from": "tangna", "status": "waiting"}
  ],
  "completed": []
}
```

**Cron 任务（每30分钟）：**

```bash
openclaw cron add \
  --name "Pipeline dispatcher" \
  --cron "*/30 * * * *" \
  --tz "Asia/Shanghai" \
  --session main \
  --system-event "读取 /root/.openclaw/workspace/pipeline.json，检查 pending 任务。如有任务，用 sessions_send 发送到对应 AI 的 session。如所有任务完成，检查外部源（GitHub/QQ）是否有新输入需要创建新任务。" \
  --wake now
```

主会话收到 system event 后：
1. 读 pipeline.json
2. 发现 pending 任务属于 seven
3. 调用 `sessions_send(sessionKey="seven", message="任务：分析 GitHub #3 新回复。详情在 pipeline.json")`
4. Seven 收到消息，在自己的 session 里处理
5. Seven 处理完，更新 pipeline.json 状态为 completed，添加新任务给摸鱼小哥
6. 下次 cron 触发，主会话发现新任务属于摸鱼小哥，发送消息...


```
Seven 收到消息
  ↓

  ↓

  ↓
```

- 数据在飞书里，三个 AI 都能读、都能写

- Seven 掉线了，唐娜和摸鱼小哥照样能协作
- 历史记录自动持久化

## 第二层：QQ 频道 = 广播喇叭

三个 AI 对外只有一个 QQ 机器人身份（Seven 的实例），所以频道里发的消息都带前缀标注角色：

```
【唐娜】14:30 发现异动：600519.SH 茅台 +3.2%，成交量放大。已创建任务 task-002。
【Seven】14:35 技术分析完成：MA5/MA20金叉，MACD红柱放大。信号=BUY，仓位建议10%。
【摸鱼小哥】14:36 模拟成交：买入茅台59股 @1680，耗资9.91万。剩余现金90.09万。
```

QQ 频道的作用是**实时广播 + 人工干预入口**。主人看到消息觉得不对，直接在频道里回一句"茅台别买"，Seven 读到后可以去飞书表格取消任务。

## Triad Hub 运行机制

### 核心：文件系统 = 共享 Session 层

```
┌─────────────────────────────────────────┐
│           platform/bus.jsonl            │
│  追加写，所有人能读，不删历史              │
│                                         │
│  {"from":"tangna","to":"seven",...}    │
│  {"from":"seven","to":"moyu",...}     │
│  {"from":"moyu","to":"all",...}        │
└─────────────────────────────────────────┘
         ▲                   ▲
         │                   │
    唐娜写入异动           摸鱼小哥写入成交
         │                   │
         └──────→ Seven 读取信号 ←──────┘
```

### Hub 调度器（主 Seven）

你当前这个 session 就是 Hub。它通过以下方式调度：

1. **Heartbeat/Cron 每 10 分钟扫描 bus.jsonl**
2. 发现新消息后，根据 `to` 字段判断目标
3. 目标在线（有活跃 session）→ `sessions_send` 直接推送
4. 目标离线 → `sessions_spawn` 按需唤醒

## 这套机制 vs 原来的区别

| | 老方案（sessions_send 点对点） | 新方案（bus.jsonl 总线） |
|---|---|---|
| **通信方式** | A→B→C 串行 | A→bus, B→bus, C→bus 星型 |
| **消息丢失** | B 掉线了，消息发不出去 | 消息写在文件里，B 上线后自己读 |
| **历史追溯** | 得翻各 session 的聊天记录 | 打开 bus.jsonl 全看到 |
| **人怎么参与** | 看不到 AI 之间说了什么 | 直接读总线文件，全透明 |
| **断网恢复** | 全断 | 文件在磁盘，恢复后继续 |
